# Pipeline benchmarks

Synthetic wallet ledgers at increasing scale, run through the **production** pipeline code (Bronze → Silver transform, Delta MERGE, Gold aggregates) on a separate benchmark lake. Generated by [`data-pipeline/bench`](../../data-pipeline/bench); reproduce with `make bench`.

**Machine:** Apple M4, 10 cores, 16 GB RAM · Spark 4.2.0 (local[*], driver 8g) · DuckDB 1.5.6 · Python 3.13.14 · run 2026-10-09 in 39 min.

## Key findings

1. **Near-linear until memory runs out.** From 1M to 20.1M rows (20× the data) the Bronze → Silver load took 25.6× as long; throughput peaked at 195k rows/s (10M rows) on one laptop. The last step (10M → 20.1M) took 3.7× as long for 2× the rows: a 16 GB machine starts spilling there, the point where a cluster (or Databricks) takes over.
2. **Incremental MERGE beats rewriting.** At 20.1M rows an insert-only MERGE took 4.54 s, 25.2× faster than the 114 s full rewrite. Scattered corrections forced MERGE to rewrite 16 files (92.88 s); with **deletion vectors** the same update rewrote 0 files and took 40.68 s (2.3× faster than without).
3. **Partitioning by month pays off for monthly reports.** The one-month report read 1 of 24 files on the month-partitioned table vs 16 of 16 unpartitioned (0.24 s vs 0.30 s, 1.3× faster).
4. **Z-ordering speeds up point lookups.** One customer's history read 2 of 178 files after Z-ordering by user_id vs 16 of 16 before (98 ms vs 0.39 s, 4.0× faster). On the month-partitioned table the same lookup took 0.41 s: a layout helps the queries it was designed for.
5. **Small files are a tax.** 25 tiny merges cost 160 s (6.4 s per commit) and grew the table from 16 to 416 files; OPTIMIZE (0.48 s) compacted it to 17, and a full scan went from 1.11 s to 0.83 s. Batch small loads and compact regularly.
6. **Right-size the engine.** The same aggregation over 20.1M rows took 0.77 s in Spark and 36 ms in DuckDB (DuckDB 21.3× faster). On one machine an in-process engine wins; Spark earns its overhead once data outgrows a node, which is why the warehouse and the admin console query with DuckDB.
7. **Tune shuffle partitions.** Building Gold at 20.1M rows with adaptive execution off: 4 partitions 42.67 s, 16 partitions 47.04 s, 200 partitions 64.56 s. 4 was fastest here; the default 200 suits clusters, and AQE (on in the pipeline) adapts this automatically.

## Method

- Data: `bench/generate.py` — skewed customers, log-normal amounts per category, month-end salaries, paired transfer legs and correct running balances (validated: 0 unbalanced transfers, 0 balance breaks).
- Every write is a single timed run; every query is the median of 3 runs after a warm-up.
- Spark `local[*]` with AQE on (except the shuffle experiment); the real lake and Postgres are never touched.
- Raw numbers: [`results.json`](results.json).
